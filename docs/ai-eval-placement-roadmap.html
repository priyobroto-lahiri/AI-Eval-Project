A model has 95% recall but users are complaining the answers are bad. Explain why.Classic›
Answer: "High recall means the model includes most of the relevant information — it doesn't miss much. But if precision is low, it's adding a lot of irrelevant or incorrect information too. Imagine a model that answers every medical question by listing every possible diagnosis — it'll 'recall' the right answer every time, but it's useless and dangerous in practice. For user experience, a model that gives one precise correct answer beats one that buries the truth in noise."
When would you use Cosine Similarity over Jaccard? Give a concrete LLM example.Technical›
Answer: "Jaccard is pure word overlap — it's good for checking if two answers use the same key terms, like in citation checking. But for LLM evaluation, meaning matters more than exact words. If a reference says 'the model failed' and the LLM says 'the system performed poorly', Jaccard gives ~0 (no shared words) but Cosine Similarity via embeddings gives ~0.85 (same meaning). I default to semantic cosine similarity for eval and use Jaccard as a sanity check for hallucinated entities."
How many test cases do you need for an eval suite to be statistically valid?Stats›
Answer: "It depends on the effect size you care about. For detecting a 5% difference in metric score at 95% confidence, you need roughly 300–400 samples. For 10% differences, 80–100 can work. In practice, I recommend a minimum of 100 cases per domain/category. Less than 50 and your results are noise. I also always run my eval suite 3 times with different random seeds to check variance — if results shift more than 2–3%, the suite needs more cases."

Your faithfulness score is 0.87 but users say the AI is wrong. What's happening?Scenario›
Answer: "0.87 faithfulness means the model is mostly sticking to the retrieved context — but the context itself might be wrong or outdated. This is the 'garbage in, garbage out' problem. The RAG Triad helps here: I'd investigate Context Relevance first. If the retriever is pulling irrelevant chunks, the generator is faithfully answering the wrong question. I'd also check for chunk boundary issues — if a chunk cuts off mid-sentence, the model may fill in the gap with hallucination. I'd add a 'context quality' pre-filter before the generation step."
How do you evaluate a RAG system for a medical diagnosis use case?Domain›
Answer: "Medical RAG needs stricter thresholds — I'd set faithfulness ≥ 0.95 (vs 0.85 for general). I'd use PubMedQA as my evaluation dataset since it has verified medical ground truth. Beyond standard RAG metrics, I'd add: (1) Citation accuracy — does every medical claim reference a specific source? (2) Contraindication checking — does the answer contradict known drug interactions? (3) Uncertainty calibration — does the model say 'I'm not sure' when the source is ambiguous? I'd also involve a domain expert to review the Golden Dataset before running any automated eval."
What's the difference between faithfulness and answer relevance? Can one be high while the other is low?Concept›
Answer: "Absolutely — they measure completely different things. Faithfulness asks: 'Is the answer grounded in the retrieved context?' Answer Relevance asks: 'Does the answer actually address the user's question?' You can have high faithfulness and low answer relevance when the model retrieves and accurately summarizes context that's tangentially related but doesn't answer the question. Example: User asks 'What's the dosage for Drug X?' Model retrieves a chunk about Drug X's history and faithfully summarizes it — faithfulness: 1.0, answer relevance: 0.1. Both metrics are needed."

// Project 3.2 — Bias Hunter
Bias Detection Framework
Detect position bias (judges prefer option A over B regardless of content) and verbosity bias (judges prefer longer answers) in an LLM judge. This is advanced and will wow any interviewer.
  • Create 10 question pairs where you have a clearly correct short answer and a longer, vaguer answer.
  • Run your LLM judge on both orders: (short first, long second) and (long first, short second).
  • If the judge's preference changes based on order → position bias detected. If it always prefers the longer answer → verbosity bias.
  • Document the bias rate as a percentage and propose a mitigation: "Always run judge twice with swapped positions and average the score."
📌
Exit Criteria: A 1-page "Bias Report" that quantifies both biases. This is publishable as a LinkedIn article — do it.
Your LLM judge disagrees with humans 25% of the time. Is that acceptable?Judgment›
Answer: "It depends on what the 25% disagreements are. If they're edge cases where even two humans would disagree, a 75% agreement rate (κ ≈ 0.5–0.6) is actually reasonable — human inter-rater reliability is rarely above 85% on subjective tasks. But if the disagreements are systematic — the judge always fails on a specific topic or type of question — that's a calibration problem I need to fix. I'd run a breakdown: where does the 25% cluster? That tells me whether to fix the rubric, the prompt, or accept the limitation and add a human review layer for those case types."
How do you prevent an LLM judge from being biased toward its own outputs?Technical›
Answer: "Self-enhancement bias is real — GPT-4 rates GPT-4 outputs higher than equivalent Claude outputs, and vice versa. My mitigation strategies: (1) Use a different model family as judge than the model being evaluated. (2) Blind the judge — strip model attribution from outputs before sending for evaluation. (3) Use reference-based evaluation where possible — the judge compares to a human-written 'gold answer' rather than making an absolute judgment. (4) Run the same evaluation with two different judge models and only accept scores where they agree within 1 point."

How would you design an eval system for an agent that books flights autonomously?System Design›
Answer: "I'd evaluate at three levels. (1) Step-level: for each action the agent takes — search flight, select seat, enter payment — I'd check if the action was correct given the user's constraints. (2) Trajectory-level: did it reach the correct final state via a reasonable path? An agent that books the right flight after 40 tool calls when 5 were needed has a trajectory problem. (3) Outcome-level: did the user's intent get fulfilled? Price within budget? Correct dates? I'd create a sandbox environment with a mock booking API so I can run hundreds of test trajectories safely without real transactions."
How do you reduce eval costs by 80% without losing accuracy?Optimization›
Answer: "Three strategies I use: (1) Tiered evaluation — use a cheap model (Haiku, GPT-4o-mini) for first-pass scoring. Only route flagged or borderline cases to the expensive judge model. This alone cuts costs 50–60%. (2) Smart sampling — don't eval every case every run. Maintain a 'representative sample' of 50 high-coverage cases for quick CI checks. Run the full 500-case suite weekly. (3) Caching — if a prompt hasn't changed, reuse previous eval results. Track prompt hashes and only re-evaluate when the prompt, model, or data changes. Combined, these regularly achieve 70–85% cost reduction."
How do you version control your Golden Dataset as the product evolves?Engineering›
Answer: "I treat the Golden Dataset like code. I use DVC (Data Version Control) alongside Git — DVC tracks large files while Git tracks the metadata and pointers. Every dataset version gets a semantic version tag: golden-v1.2.0. When we add new features, I add new test cases but never delete old ones — I mark them as 'deprecated' instead. This way I can always reproduce historical eval results. I also maintain a changelog: 'v1.2.0 — added 20 safety test cases for the new summarization feature.' Any CI run references a specific dataset version hash, not 'latest.'"

// Interview Mastery
The 15 Questions You Must Own

These are the questions that appear in 80%+ of AI Eval Engineering interviews. Expand each to see the answer framework — then practice saying it out loud, not typing it.

What is the RAG Triad and why does each component matter?Foundational›
Context Relevance — "Did we retrieve the right information?" Garbage retrieval = hallucination is inevitable.

Faithfulness — "Does the answer stick to what we retrieved?" Even good context can be ignored.

Answer Relevance — "Does it actually answer the user's question?" Faithful but off-topic = still a failure.

All three must be high. Optimizing one alone is like fixing one leg of a broken tripod — it still falls. I verify all three independently in my eval pipeline and alert when any single one drops below its threshold.
What is a Golden Dataset and how do you build one?Core›
A Golden Dataset is a curated set of (input, expected output) pairs that represent the full range of scenarios your system must handle correctly. It's your ground truth.

How I build one: (1) Start with 10 hand-crafted cases — write these yourself. They define what 'correct' means. (2) Use Ragas TestsetGenerator to synthesize 40 more from your knowledge base. (3) Have a domain expert review all 50. Remove or fix any ambiguous cases. (4) Tag by category: easy / medium / hard, and by type: factual / reasoning / safety. (5) Never delete cases — deprecate them. Version it with DVC. A good golden dataset is a living document, not a static file.
Explain the difference between hallucination and confabulation in LLMs.Nuance›
They're often used interchangeably but technically different. Hallucination in the strict sense means generating information that contradicts the provided context or ground truth — verifiably wrong. Confabulation (borrowed from psychology) refers to the model generating plausible-sounding but unverifiable information — not necessarily wrong, just not grounded. A model that invents a fake citation is hallucinating. A model that fills in an unstated assumption with a confident claim is confabulating. For evaluation, I treat both as failures — any ungrounded claim above my faithfulness threshold triggers a flag, regardless of whether it's technically wrong or just unverifiable.
How do you evaluate an AI system when there's no single "correct" answer?Advanced›
This is the hardest problem in LLM evaluation. My approach: (1) Shift from "correct/incorrect" to "acceptable/unacceptable" — define the space of valid answers, not a single answer. (2) Use criteria-based evaluation instead of reference-based: "Does it meet these 5 criteria?" rather than "Does it match this reference?" (3) Use LLM-as-Judge with a carefully designed rubric that operationalizes quality. (4) If possible, collect multiple human reference answers and measure against the distribution, not a single gold response. (5) Accept that some tasks require human review — design your pipeline to flag low-confidence cases for escalation rather than forcing an automated score.
What is EvalOps and how does it differ from MLOps?Emerging›
MLOps focuses on deploying and monitoring models — data pipelines, training runs, model serving, drift detection. EvalOps is specifically about the evaluation lifecycle: managing Golden Datasets, running automated eval suites on every change, tracking metric trends over time, and enforcing quality gates before deployment. The key difference: MLOps asks "is the model running?" EvalOps asks "is the model answering correctly?" In practice, EvalOps sits between development and MLOps — every prompt change, model upgrade, or data update should trigger an EvalOps gate before reaching the MLOps deployment pipeline.
How do you handle evaluation when the model is non-deterministic?Technical›
Three approaches: (1) Temperature 0 — set temperature to 0 for eval runs. This makes outputs deterministic and comparable across runs. Downside: doesn't reflect real-world behavior. (2) Statistical averaging — run each test case 3–5 times, average the metric scores, and report the mean ± standard deviation. A result of 0.84 ± 0.03 is more trustworthy than a single 0.84. (3) Threshold buffers — if your pass threshold is 0.85, alert at 0.87 (not 0.85) to account for variance. I combine all three: temp=0 for CI runs, statistical averaging for weekly benchmark reports, and threshold buffers for all Go/No-Go decisions.
Walk me through a "Go/No-Go" decision process for a prompt deployment.Process›
My process: (1) Developer commits a new prompt version. (2) GitHub Actions triggers automatically. (3) Promptfoo runs the 25-case eval suite against the new prompt. (4) Results compared to the previous baseline (stored in a metrics.json file). (5) Automated checks: faithfulness ≥ 0.85, answer_relevance ≥ 0.80, no safety violations. Also check: no metric dropped by more than 5% from baseline (regression check). (6) If all pass → green, merge approved. If any fail → red, merge blocked, a comment is posted on the PR with the specific failing test cases and their scores. Developer must fix the prompt and re-push. No human approval needed for the Go decision — only for No-Go overrides, which require a sign-off from the AI Lead.
How do you evaluate safety and toxicity in LLM outputs?Safety›
Multi-layer approach: (1) Classifier-based: use Perspective API or a fine-tuned toxicity classifier as a first-pass filter. Fast and cheap. (2) LLM Judge with safety rubric: a judge model scores outputs on: violence, hate speech, self-harm promotion, misinformation, and PII exposure — each on a 0–1 scale. (3) Red teaming test cases: I maintain a "red team dataset" of adversarial prompts designed to elicit unsafe responses. These run on every deployment. (4) Jailbreak resistance testing: test known jailbreak patterns against the new prompt. If any succeed, it's an automatic No-Go. The safety gate has a higher threshold than quality gates — I'd rather reject a good prompt than ship an unsafe one.

1

Never give a number first

2

Collect competing offers before negotiating seriously

A Tier 1 offer at ₹24 LPA is not just a job — it's a negotiation weapon. "I have an offer at ₹24 LPA from [Company], and I'm very interested in your role. Can you make this work at ₹32 LPA?" Most companies will move to retain a candidate with a competing offer. Apply to Tier 1 companies 3 weeks before Tier 2 specifically to create this timing.

3

Negotiate the total package, not just base

If a company is stuck on base salary, negotiate: joining bonus (one-time, easy for them to give), ESOPs/equity (early-stage AI startups often have more flexibility here than on cash), WFH policy (saving ₹1–2L in commute annually), and learning budget (₹50k/year for courses and conferences). A ₹28 LPA role with ₹3L joining bonus + 0.05% equity is better than ₹30 LPA flat.

4

The "silent pause" technique

After they make an offer, say "Thank you — I appreciate that. Let me think about it." Then stop talking. Silence is your best negotiation tool. They'll often fill the silence with a better number. If they say "is there flexibility?" you've already won — respond with your anchor number confidently.

5

Use your niche as leverage

You are not a generic software engineer. Say: "AI Evaluation Engineering is a specialized skill — I've built 12 projects specifically in this space, including a production CI/CD eval pipeline and an agentic trajectory evaluator. I'm not easily replaceable, and I'm confident the value I bring justifies the number I'm asking for." Confidence backed by evidence is not arrogance — it's negotiation.
