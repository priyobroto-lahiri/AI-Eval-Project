// Month 1 · Statistical Foundations
Text Similarity Engine — 4 Methods Benchmarked
Move from Boolean (pass/fail) to Statistical (scored) testing. Build an engine that compares LLM output to ground truth using 4 different similarity algorithms.
~$0.05
API cost
// Why this phase exists
Before you can evaluate if an LLM is "good," you need mathematical tools to measure similarity. A human can read two answers and say "that's close enough." But an automated pipeline needs a number between 0 and 1. This phase gives you 4 different ways to produce that number — and the judgment to know when each one is appropriate.
Week 1
Jaccard + TF-IDF Cosine Similarity
Tools: Python, NumPy, scikit-learn. No API needed — pure math.
▶
// Concepts to learn
Jaccard Similarity — intersection over union of word sets. Fast, interpretable, ignores word order.
TF-IDF — term frequency × inverse document frequency. Weights rare words higher.
Cosine Similarity — angle between two vectors in high-dimensional space. The gold standard for text.
Precision vs Recall — can you explain why 100% recall might still be a bad answer?
// Build targets
Function: jaccard(a, b) → float — tokenize, compute overlap
Function: cosine_tfidf(a, b) → float — TfidfVectorizer + cosine_similarity
Test on 5 sentence pairs — same meaning, different words (paraphrases)
Observe: Jaccard scores paraphrases low (~0.1). TF-IDF scores them medium (~0.4). Note the gap.
Week 2
ROUGE-L + Semantic Similarity (MiniLM)
Tools: rouge-score, sentence-transformers. Add meaning-based scoring.
▶
// Concepts to learn
ROUGE-L — longest common subsequence. Used in summarization eval. Captures structure, not just word overlap.
Sentence embeddings — MiniLM model converts sentences into 384-dimension vectors that capture semantic meaning.
Cosine on embeddings — the vector angle trick applied to meaning, not words.
// Build targets
Function: rouge_l(a, b) → float — use rouge-score library
Function: semantic(a, b) → float — SentenceTransformer("all-MiniLM-L6-v2")
Test all 4 methods on same 20 sentence pairs — create comparison DataFrame

Week 1
RAG Triad Theory + ChromaDB Setup
Learn the 3 metrics that matter. Build a working RAG pipeline with PubMedQA as the knowledge base.
▶
// The RAG Triad — memorize these
Context Relevance (0–1) — Is the retrieved chunk actually relevant to the question? Measures retrieval quality.
Faithfulness (0–1) — Does the answer stay true to what's in the retrieved context? Catches hallucination.
Answer Relevance (0–1) — Does the final answer actually address the question? Measures completeness.
// Build: RAG pipeline with ChromaDB
Load 50 PubMedQA documents into ChromaDB vector store
Set up retrieval: question → top-3 chunks
Generate answers using Gemini Flash (dev mode — free)
Manually verify 5 answers — are they faithful to the source?
Week 2
Ragas Scoring + Hallucination Flag System
Automate the scoring. Flag any answer with faithfulness below 0.7 as a hallucination risk.
▶
// What to learn
Ragas library — evaluate(dataset, metrics=[faithfulness, answer_relevancy, context_relevancy])
Dataset format — Ragas needs: question, contexts (list), answer, ground_truth
Threshold setting — faithfulness < 0.7 = hallucination flag. Why 0.7 and not 0.9? Understand the tradeoff.
// Build: hallucination reporter
Run Ragas on 50 PubMedQA Q&A pairs
Flag all answers where faithfulness < 0.7
Save report: question, faithfulness_score, flag, reason
Find the worst-performing question — why did it hallucinate?

Bias Detection — Position + Verbosity
Detect when the judge is scoring based on answer position or length rather than quality. Quantify it.
▶
// Two biases to detect
Position bias — LLM judges prefer whichever answer appears first (Answer A vs Answer B). Test by swapping order and checking if score changes.
Verbosity bias — LLM judges prefer longer answers even when shorter is more accurate. Test by padding a wrong answer with extra words.
// Build targets

Verbosity bias test: 10 short correct vs 10 long wrong → which does judge prefer?
